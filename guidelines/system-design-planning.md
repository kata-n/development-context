# 🧭 設計レビュー前の事前準備テンプレート

## 1. 🎯 設計のゴール（Why / What）

- **この設計は何を解決するためのものか？**

  - 例：「Firestore 保存と Cloud Storage の整合性を担保するため」

- **なぜ今これを設計する必要があるのか？**
  - 例：「UI 操作とデータ保存の責任分離ができておらず、仕様バグが起きていたため」

---

## 2. 🛣 背景と制約条件（Context）

- 前提としている仕様・実装制約：

  - 例：「通信断あり得る」「複数タブ対応」「Firestore でサブコレクションは使わない」

- 過去の設計方針や影響範囲：
  - 例：「既存の`RequestCollection`構造を変えない前提」

---

## 3. 🔁 状態遷移の概要（if applicable）

- 対象の状態名（enum や status 名）：

  - 例：「`uploaded` / `softDeletedHidden` / `draftOnly`」

- 主要なイベント・操作と状態の変化：
  - 例：「ファイルアップロード → `uploaded`」「保存 → Firestore へ反映」

※ `mermaid` などで図示できるなら尚良い

---

## 4. 🧠 設計判断の軸と比較（Why this design?）

| 軸               | 今回の設計                             | 別案（採用しなかったもの） | コメント                           |
| ---------------- | -------------------------------------- | -------------------------- | ---------------------------------- |
| 通信断対応       | ✅ ローカルで一時保持 → 保存時書き込み | ❌ 即保存                  | 通信不安定時の誤保存防止           |
| 実装コスト       | 中                                     | 低                         | 一部既存コードの再利用でカバー可能 |
| Firestore の制約 | クエリ可能・非正規化                   | サブコレ使用               | クエリ不可リスク回避のため不採用   |

---

## 5. ❓ 想定質問と回答メモ（FAQ）

| 想定される質問                   | 回答の要点                                 |
| -------------------------------- | ------------------------------------------ |
| なぜアップロード時に保存しない？ | ユーザー意志の明示と整合性担保を優先       |
| `softDeletedHidden` って必要？   | 履歴保持と画面表示制御を分離するため必要   |
| 複数タブでの整合性は？           | Firestore 状態ベースで判断し、競合抑止済み |

---

> そのために、Firestore への書き込みを保存時に限定しています。」
